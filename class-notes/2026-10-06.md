# 수업 정리 (2026-10-06) · 김용담 선생님

## 1. 모델 크기

- 파라미터 수 단위: **B = billion(10억)**, **T = trillion(1조)**. 예: 7B = 70억 개, 1.8T = 1조 8천억 개.
- small / large 모델을 나누는 **공식 기준은 없다.** 선생님 기준으로는 대략 **20~30B 정도**를 경계로 본다.
  (자료에 따라 sLM을 10B 이하로 부르기도 하니 "대략적인 감"으로 기억해 두면 된다.)

## 2. MoE (Mixture of Experts): 파라미터는 크게, 연산은 적게

- 모델 안에 **여러 개의 전문가(expert) 하위 네트워크**를 두고, **토큰마다 그중 일부(보통 1~2개)만 골라** 계산하는 구조.
- 트랜스포머에서는 각 층의 **FFN을 여러 개의 expert FFN으로 바꾸고**, attention은 그대로 공유한다.
- **라우터(router, gating network)**가 토큰을 보고 어떤 expert로 보낼지 정한다(top-k 선택).
- 그래서 **전체 파라미터 수는 크지만, 토큰 하나를 처리할 때 실제로 쓰는(active) 파라미터는 일부**라서 연산량이 작다.
  - 예: 전체 수백 B인데 토큰당 active는 수십 B인 식.
- 주의: 연산은 줄어도 **모든 expert를 메모리(GPU)에 올려 둬야** 하므로 메모리 요구량은 줄지 않는다.

## 3. 검색의 종류: Table lookup vs IR, 검색 vs 추천

- **Table lookup**: RDB에서 SQL 쿼리로 조건에 맞는 행을 정확히 찾는 것. (`WHERE id = 3` 같은 정형 데이터 조회)
- **IR (Information Retrieval, 정보 검색)**: 문서 같은 비정형 텍스트에서 질문과 **관련도가 높은 것을 순위대로** 찾는 것. RAG의 검색이 여기에 해당한다.
- 둘은 보통 별개 카테고리로 보지만, 넓게는 lookup을 IR의 일부로 부르기도 한다.
- **검색 vs 추천**
  - 검색: 사용자가 **쿼리(질문)를 명시적으로 준다.** "이걸 찾아줘".
  - 추천: 쿼리 없이 **사용자의 이력·취향·행동 데이터**로 좋아할 만한 것을 골라 준다.
  - 추천이 어려운 예: 여성 뷰티·여성 패션은 취향 범주가 너무 다양하고 들쭉날쭉해서 순위 매기기가 특히 어렵다.

## 4. Inverted Index (역색인)

- **단어 → 그 단어가 들어 있는 문서 번호 목록**으로 저장해 둔 구조. 책 맨 뒤의 "찾아보기(색인)"와 같다.
  ```
  "강아지" → [문서1, 문서4, 문서7]
  "고양이" → [문서2, 문서4]
  ```
- 쿼리가 오면 쿼리의 단어로 목록을 바로 꺼내므로, 모든 문서를 다 읽지 않아도 된다.
- 단어가 글자 그대로 일치해야 찾는 **exact (lexical) matching** 방식이다. "강아지"로 검색하면 "반려견"만 있는 문서는 못 찾는다.

## 5. TF-IDF

- 어떤 단어가 한 문서에 많이 나온다고 꼭 중요한 단어는 아니다. "the", "은/는", "있다"처럼 **모든 문서에 다 나오는 단어**는 구별력이 없다.
- 그래서 "이 문서에 많이 나오는데(TF↑), 다른 문서에는 잘 안 나오는(DF↓)" 단어에 높은 점수를 준다.
- 용어
  - **TF (Term Frequency)**: 특정 문서 안에서 특정 단어가 나온 횟수.
  - **DF (Document Frequency)**: 그 단어가 나온 문서의 개수. 단어마다 값이 하나다.
  - **IDF (Inverse DF)**: `log(전체 문서 수 / DF)`. DF가 작을수록(희귀할수록) 커진다.
  - **TF-IDF = TF × IDF**
- **TF-IDF 행렬**: 행 = 문서, 열 = 단어(어휘), 각 칸 = 그 문서에서 그 단어의 TF-IDF 값. 문서 하나가 "어휘 크기만큼 긴 벡터" 하나가 된다.
- 결론: **TF는 크고 DF는 작은 단어**가 그 문서의 키워드다.
- 참고: 실무에서는 TF-IDF를 개선한 **BM25**를 sparse 검색의 기본으로 많이 쓴다.

## 6. 검색 평가 지표: Recall@K, MRR

- **Recall@K**: 상위 K개 결과 안에 정답 문서가 들어 있는 비율. 안에 **있기만 하면** 1등이든 K등이든 똑같이 친다.
- **MRR (Mean Reciprocal Rank)**: **첫 번째 정답의 순위**만 보고 `1 / 순위`를 계산해 질문들에 대해 평균 낸다.
  - 정답이 1등이면 1, 2등이면 0.5, 5등이면 0.2.
  - 그래서 정답을 **얼마나 위에** 올렸는지가 반영된다.
- 예: K=5에서 정답이 4등 → Recall@5 = 1(들어 있음), RR = 0.25.

## 7. Sparse Retrieval vs Dense Retrieval

### Sparse retrieval (TF-IDF, BM25)

- 벡터의 차원이 **어휘(단어 사전) 크기**만큼이라 수만~수십만 차원인데, 한 문서에 나오는 단어는 일부라 **대부분이 0**이다. 그래서 "sparse(희소)".
  (실제로는 0을 다 저장하지 않고 역색인으로 저장하므로 저장은 효율적이다.)
- 쿼리와 문서에 **같은 단어가 겹쳐야** 점수가 생긴다. 동의어·다른 표현은 못 잡는다(어휘 불일치 문제).
- **전처리의 영향을 많이 받는다.** 토큰을 어떻게 자르는지, 불용어 처리, 한국어는 형태소 분석기 선택에 따라 결과가 크게 달라진다.
- 장점: 고유명사, 제품 코드, 숫자 같은 **정확한 키워드**는 잘 찾는다.

### Dense retrieval

- **BERT 계열 인코더**로 문장 전체를 수백~수천 차원의 **촘촘한(대부분 0이 아닌) 벡터(임베딩)**로 바꿔서, 벡터끼리 가까운 것을 찾는다.
- 의미가 비슷하면 단어가 달라도 가깝게 놓인다. ("강아지" ↔ "반려견")
- 신경망이 sparse 벡터를 변환해서 dense를 만드는 게 아니라, **텍스트에서 바로** dense 벡터를 뽑는다.

### 공통 규칙

- 어느 방식이든 **쿼리와 문서는 같은 변환 규칙**으로 벡터로 만들어야 비교할 수 있다.
  - sparse: 같은 토크나이저·같은 어휘 사전
  - dense: 같은 임베딩 모델 (모델을 바꾸면 문서 임베딩을 전부 다시 만들어야 한다)

### 유사도 계산

- **코사인 유사도**: 두 벡터 사이의 **각도**. 방향이 완전히 같으면 1, 직교하면 0, 정반대면 -1. 클수록 비슷하다.
- **유클리디안 거리**: 두 점 사이의 **직선 거리**. 작을수록 비슷하다.
- 벡터 길이를 1로 정규화하면 두 방식의 순위가 같아진다.

### Offline / Online

- **Offline(사전 작업)**: 검색 요청이 오기 전에 미리 해 두는 것. 문서 청킹 → 임베딩 → 인덱스 구축.
- **Online(검색 시점)**: 쿼리가 오면 쿼리만 임베딩해서 인덱스에서 찾는다.

## 8. Sentence-BERT (SBERT)

- **BERT**: 문장 중간 단어를 가리고 맞히는 **빈칸 채우기(MLM)**로 사전학습한 모델. 토큰 단위 표현은 좋지만, 그대로 문장 임베딩으로 쓰면 문장 간 유사도가 잘 안 맞는다.
- **Sentence-BERT**: BERT를 **문장 쌍**으로 추가 학습시켜, 문장 하나를 의미 있는 벡터 하나로 만들도록 한 모델. 토큰 벡터들을 평균(pooling)해서 문장 벡터를 만든다.
- 학습 방식은 **대조 학습(Contrastive Learning)** 계열: 의미가 비슷한 문장 쌍은 가깝게, 관련 없는 문장은 멀게 벡터를 배치하도록 학습한다.

## 9. Bi-encoder vs Cross-encoder

| | Bi-encoder | Cross-encoder |
|---|---|---|
| 입력 | 쿼리와 문서를 **각각 따로** 인코딩 | 쿼리와 문서를 **한 입력으로 붙여서** 인코딩 |
| 출력 | 벡터 2개 → 코사인 유사도 | 관련도 점수 1개 |
| 문서 벡터 미리 계산 | 가능 (offline) | 불가능 |
| 속도 | 빠름 | 느림 |
| 정확도 | 상대적으로 낮음 | 높음 (쿼리-문서 단어끼리 self-attention) |
| 용도 | 1차 검색 (수백만 문서 중 후보 추리기) | 2차 **리랭킹** (상위 수십 개 재정렬) |

- **Bi-encoder**: 쿼리 인코더와 문서 인코더로 각각 벡터를 만들고, 비슷한 쌍이 코사인 유사도로 가깝게 위치하도록 학습한다. 두 인코더는 따로 둘 수도 있고 같은 모델(가중치 공유)을 쓸 수도 있다.
- **Cross-encoder**: 쿼리와 문서를 `[CLS] 쿼리 [SEP] 문서` 처럼 이어 붙여 **한 모델에** 넣고, 둘 사이의 관계를 attention으로 직접 본다.
  - 단점: 점수를 내려면 쿼리가 있어야 하므로 문서 벡터를 미리 만들어 둘 수 없다. 쿼리가 올 때마다 **모든 (쿼리, 문서) 쌍마다 모델을 다시 돌려야** 해서 느리다.
- 실무 패턴: **bi-encoder로 상위 K개 후보 → cross-encoder로 재정렬**.

## 10. 임베딩 모델 고르기

- OpenAI API의 **`text-embedding-3-small`**이 싸서 많이 쓰인다.
- 임베딩 품질은 모델이 학습한 데이터(언어, 도메인)에 따라 달라지므로, 도메인에 맞는 모델을 고르기도 한다(법률, 의료, 코드 등).
- **언어를 많이 탄다.** 영어 위주로 학습된 모델은 한국어 성능이 떨어질 수 있으니, 한국어 데이터면 다국어 모델(예: bge-m3, multilingual-e5 계열)을 같이 비교해 본다.
- 모델 하나를 골라 **파인튜닝**하기도 한다. 이때는 (질문, 정답 문서) 쌍 같은 학습 데이터셋이 필요하다.
- 공개 벤치마크로는 MTEB 리더보드를 참고하면 된다.

## 11. 벡터 DB와 벡터 인덱스

### 벡터 DB

- 임베딩 벡터를 저장하고 유사도 검색을 해 주는 DB.
- 테스트·학습용으로는 **ChromaDB**를 많이 쓴다. 별도 서버 없이 로컬 파일로 돌아가서, RDB로 치면 SQLite 같은 위치다.
- 운영 환경에서는 Qdrant, Milvus, Weaviate, Pinecone, pgvector(PostgreSQL 확장) 등을 쓴다.

### 인덱싱의 목적

- 모든 벡터와 하나하나 거리를 재면(brute force, Flat) 정확하지만 문서가 많아지면 너무 느리다.
- 인덱스는 **search space(뒤져야 할 범위)를 빠르게 줄여 주는 것**이 목적이다.

### 왜 단순한 공간 분할이 안 되나

- 저차원에서는 **k-d tree**처럼 공간을 잘게 나눠 가까운 영역만 보면 된다.
- 하지만 임베딩처럼 **차원이 높으면(차원의 저주)** 점들 사이 거리가 다 비슷비슷해져서, 영역을 나눠도 쿼리 근처 "원"에 걸리는 영역이 너무 많아져 결국 거의 다 뒤져야 한다.
- 그래서 고차원에서는 그래프 기반(HNSW)이나 클러스터 기반(IVF) 인덱스를 쓴다.

### HNSW (Hierarchical Navigable Small World)

- **Small world 가정**: 노드들이 이웃과 연결을 맺다 보면, 몇 단계만 건너도 어떤 노드에든 도달할 수 있는 "좁은 세상" 그래프가 된다. (6단계만 거치면 누구와도 아는 사이라는 이야기와 같은 원리)
- **Hierarchical(계층)**: 그래프를 여러 층으로 쌓는다.
  - 위층: 노드가 적고 연결이 길다(고속도로).
  - 아래층: 모든 노드가 있고 연결이 촘촘하다(골목길).
- 검색 방법(greedy search)
  1. 맨 위층의 **entry point**에서 시작한다.
  2. 현재 노드의 이웃 중 **쿼리 벡터와 가장 가까운 노드로 이동**한다. 더 가까운 이웃이 없을 때까지 반복.
  3. 한 층 아래로 내려가서 같은 과정을 반복한다.
  4. 맨 아래층에서 찾은 가장 가까운 노드들이 결과다.
- 이렇게 쿼리와 가까운 노드로 범위를 좁혀 가므로 전체를 다 보지 않아도 된다.

### ANNS (Approximate Nearest Neighbor Search)

- HNSW 같은 방식을 **근사 최근접 이웃 검색**이라고 부른다.
- "근사"인 이유: 진짜 가장 가까운 벡터를 **100% 보장하지는 않는다.** 대신 아주 빠르다. 정확도를 조금 포기하고 속도를 얻는 trade-off다.
- 근사 결과가 정답(brute force 결과)을 얼마나 맞히는지를 recall로 측정하고, HNSW 파라미터(`M`, `ef_search` 등)로 속도와 정확도를 조절한다.

## 원래 메모에서 고친 부분

1. **"MOE 아키텍쳐는 전문가 노드만 몇개 두고 전체 노드를 신경망에서 쓰게 하지 않는것"**
   expert는 "노드"가 아니라 **FFN 하위 네트워크 단위**이고, 라우터가 **토큰마다** 어떤 expert를 쓸지 고른다. 또 연산은 줄지만 전체 파라미터는 메모리에 다 올려야 한다는 점을 덧붙였다.
2. **"Inverted index: 입력받은 단어의 문서의 번호를 index를 추출"**
   역색인은 검색 시점에 뭔가를 추출하는 게 아니라, **미리 "단어 → 문서 번호 목록"으로 만들어 둔 자료구조**다. 검색할 때는 그 목록을 꺼내 쓰기만 한다.
3. **"TF: x축은 단어 횟수, y축은 문서 개수 / DF: y축으로만 표현"**
   축 설명이 헷갈리게 적혀 있었다. TF-IDF 행렬은 **행 = 문서, 열 = 단어, 칸 = 점수**다. TF는 (문서, 단어) 칸마다 값이 있고, DF는 **단어마다 값 하나**라서 한 줄짜리 벡터로 표현된다. IDF와 TF×IDF 공식도 추가했다.
4. **"Sparse retrieval은 모든 경우의 수를 전부 벡터에 넣기 때문에 낭비가 심하다"**
   정확히는 벡터 차원이 **어휘 크기만큼 커서 대부분이 0**인 것이다. 실제 저장은 역색인으로 0을 빼고 하므로 낭비가 심하지 않다. sparse의 진짜 약점은 **단어가 안 겹치면 못 찾는 것**(동의어 문제)이다.
5. **"코사인 유사도: 완전히 같을때 1, 직교할때 0"**
   맞다. 정반대 방향이면 -1이라는 것과, 유클리디안 거리는 작을수록 비슷하다는 점을 보충했다.
6. **"sparse를 neural network를 이용해서 dense를 만든다?"**
   아니다. dense 벡터는 sparse 벡터를 변환하는 게 아니라 **인코더 모델이 텍스트에서 바로** 만든다.
7. **"Dense와 sparse는 매칭을 위해 동일한 변환규칙을 쓴다"**
   dense와 sparse가 서로 같은 규칙을 쓴다는 뜻이 아니라, **각 방식 안에서 쿼리와 문서가 같은 변환 규칙**(같은 토크나이저, 같은 임베딩 모델)을 써야 한다는 뜻이다.
8. **"Sentence bert는 문장들 사이의 관계를 학습"**
   방향은 맞다. 정확히는 BERT를 문장 쌍 데이터로 추가 학습시켜 **문장 하나를 벡터 하나로** 잘 만들게 한 모델이고, 그 벡터 간 거리가 의미 유사도를 반영하게 된다.
9. **"Query encoder와 document encoder를 따로 만들어서"**
   따로 둘 수도 있지만 SBERT처럼 **같은 모델 하나를 공유**하는 경우도 많다. 핵심은 쿼리와 문서를 **따로 인코딩**한다는 점이다.
10. **"Cross encoder 단점: offline단계에서 모든 쿼리를 다 알고 있어야 self attention이 가능함"**
    의도는 맞지만 표현을 바로잡았다. 쿼리를 미리 알 수 없으니 **문서 벡터를 offline에 미리 만들어 둘 수 없고**, 쿼리가 올 때마다 모든 (쿼리, 문서) 쌍에 모델을 돌려야 해서 느리다는 것이 단점이다. 그래서 리랭킹 용도로만 쓴다.
11. **"openAPI의 text-embedding-3-small"**
    **OpenAI** API다. (OpenAPI는 API 명세 표준 이름이라 다른 것이다.)
12. **"벡터인덱스를 만들려면 d tree?? 구조를 알아야한다"**
    **k-d tree**(k-dimensional tree)로 보인다. 다만 k-d tree는 고차원에서 성능이 크게 떨어져서, 임베딩 검색에는 HNSW 같은 방식을 쓴다는 흐름으로 정리했다. (선생님이 다른 구조를 말씀하셨다면 확인 필요)
13. **"차원이 높으면 클러스터링으로 유사한 애들을 잡으면 데이터가 거의 다 잡히기 때문에 원을 잡지 못함"**
    고차원에서 문제가 되는 건 주로 k-d tree 같은 **공간 분할 방식**이다. 클러스터링 기반 인덱스(IVF)는 고차원에서도 실제로 많이 쓰인다. 그래서 "공간 분할로는 범위가 잘 안 줄어든다"로 정리했다.
14. **"entry point를 랜덤으로 잡고"**
    HNSW에서 랜덤한 건 **노드가 몇 층까지 올라갈지 정하는 것(삽입 시점)**이고, 검색은 **맨 위층의 정해진 entry point**에서 시작한다. 그리고 "층을 내려가며 좁힌다"는 계층(Hierarchical) 구조 설명을 추가했다.
