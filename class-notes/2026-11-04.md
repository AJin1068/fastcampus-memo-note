## 1. 하네스(Harness)란

### 정의

- **하네스 = 모델을 둘러싼 모든 장치.** 모델 자체(가중치)를 빼고, 에이전트가 일을 처음부터 끝까지(end to end) 해낼 수 있게 만드는 바깥 구조 전체를 말한다.
  - 시스템 프롬프트, 지침 문서(CLAUDE.md 등), 도구(tool) 정의와 구현, 컨텍스트 관리, 권한·안전 규칙(hooks), 검증·평가 루프, 서브 에이전트 구성, 모델 선택까지 모두 하네스다.
  - 흔히 쓰는 비유: **에이전트 = 모델 + 하네스.** 같은 모델이라도 하네스가 좋으면 훨씬 잘한다. Claude Code, Cursor, Codex CLI 같은 코딩 에이전트도 결국 "모델 + 잘 만든 하네스"다.
- **하네스 엔지니어링**은 프롬프트 한 줄을 다듬는 수준(프롬프트 엔지니어링)이나 무엇을 넣을지 고르는 수준(컨텍스트 엔지니어링)을 넘어서, **사람이 중간에 덜 끼어들어도 에이전트가 끝까지 일을 맡아 할 수 있도록 환경 전체를 설계하는 일**이다.

### 보충: 왜 요즘 "하네스"를 말하나

- 모델이 똑똑해지면서 "한 번 묻고 한 번 답하기"보다 **긴 작업(몇십~몇백 번의 도구 호출)을 맡기는 쓰임**이 늘었다. 긴 작업에서는 11/2에 배운 **누적 오류**가 커지기 때문에, 모델을 믿는 것만으로는 부족하고 **바깥에서 잡아 주는 장치**가 필요하다.

## 2. Generator와 Evaluator

- **Generator**: 실제로 결과물(코드, 문서, 답)을 만드는 에이전트.
- **Evaluator**: 결과물이 기준을 만족하는지 판정하는 에이전트. 판정이 FAIL이면 피드백과 함께 Generator에게 되돌린다(11/2 Reflexion의 actor ↔ evaluator 구조와 같다).
- **Evaluator는 보통 Generator와 다른 모델(또는 최소한 다른 컨텍스트·프롬프트)을 쓴다.**
  - 이유 1: **자기 선호 편향(self-preference bias).** 같은 모델은 자기가 쓴 글을 더 좋게 평가하는 경향이 있다(11/3 LLM judge의 bias와 같은 이야기).
  - 이유 2: 같은 대화 맥락을 공유하면 Generator가 했던 **잘못된 가정을 Evaluator도 그대로 믿기 쉽다.** 그래서 같은 모델을 쓰더라도 **새 컨텍스트에서 결과물만 보고** 평가하게 하는 것이 기본이다.
  - 필수 규칙은 아니다. "다른 모델이어야 한다"보다 **"생성한 쪽의 맥락과 분리되어야 한다"**가 핵심이다.

## 3. Guides(feedforward)와 Sensors(feedback)

하네스가 에이전트를 제어하는 방법은 크게 두 단계로 나눈다(마틴 파울러 블로그의 Birgitta Böckeler 글 등에서 쓰는 분류).

| 구분 | 언제 작동 | 무엇 | 예시 |
|---|---|---|---|
| **Guides (feedforward)** | 행동 **전**에 방향을 알려 줌 | "이렇게 해라"라고 미리 알려 주는 것 | 시스템 프롬프트, CLAUDE.md, 코딩 규칙 문서, skill, 예시 코드 |
| **Sensors (feedback)** | 행동 **후**에 결과를 보고 바로잡음 | 실제 결과를 측정해서 알려 주는 것 | 테스트 실행, 린터·타입 체커, 빌드, hooks, Evaluator, 리뷰 |

- 둘 다 다시 **계산적(computational)**과 **추론적(inferential)**으로 나눌 수 있다.
  - 계산적: 코드로 결정되는 것. 테스트, 린터, 정규식 검사. **빠르고, 매번 같은 결과.**
  - 추론적: LLM이 판단하는 것. LLM judge, AI 코드 리뷰. 유연하지만 **결과가 흔들릴 수 있다.**

### 요즘 흐름: Sensor로 마지막 제어를 강하게

- Guide는 결국 **"부탁"**이다. 모델이 지킬 수도 있고 안 지킬 수도 있다(확률적).
  - 모델의 reasoning이 강해질수록 **지침보다 자기 판단을 우선**하는 경우가 생긴다. "이 상황엔 규칙보다 이게 낫겠다"고 스스로 판단해 버린다.
  - 작업이 길어지면 앞쪽 지침이 **긴 컨텍스트 속에 묻혀서** 덜 지켜지기도 한다.
- Sensor는 **결과를 실제로 확인**하므로, 모델이 지침을 무시해도 마지막에 잡아낼 수 있다. 그래서 요즘은 "지침을 더 길게 쓰기"보다 **"끝에서 확실하게 검사하기"**에 힘을 쏟는 추세다.
- 그렇다고 Guide가 필요 없다는 건 아니다. Guide가 없으면 처음부터 엉뚱한 방향으로 가서 Sensor에 계속 걸리고 **재시도 비용**이 커진다. **Guide로 방향을 잡고, Sensor로 최종 보장**하는 조합이다.

## 4. 에이전트의 본질은 Tool calling

- 에이전트가 하는 일은 결국 **"언제, 어떤 도구를, 어떤 인자로 부를지 정하기"**의 반복이다. 그래서 **도구 정의와 구현이 에이전트 성능을 크게 좌우한다.**

### 보충: 좋은 도구 정의·구현의 조건

- **이름과 설명이 명확할 것.** 모델은 도구 설명(description)만 보고 쓸지 말지 고른다. 언제 쓰는지, 언제 쓰면 안 되는지까지 적는다.
- **도구끼리 역할이 겹치지 않을 것.** 비슷한 도구가 여러 개면 모델이 헷갈려서 잘못 고른다.
- **인자는 단순하고 타입이 분명할 것.** enum이나 예시 값을 주면 잘못된 인자가 줄어든다.
- **결과는 짧고 필요한 것만.** API 응답 JSON을 통째로 돌려주면 컨텍스트를 낭비한다. 필요한 필드만 추리고, 결과가 크면 잘라서(페이지 나누기) 돌려준다.
- **에러 메시지가 다음 행동을 알려 줄 것.** "Error 400"보다 "date는 YYYY-MM-DD 형식이어야 함. 받은 값: 11/4"처럼 쓰면 모델이 스스로 고쳐서 다시 부른다.
- **사람이 쓰기 편한 단위로 묶을 것.** 저수준 API를 1:1로 노출하기보다, 자주 같이 쓰는 동작을 하나의 도구로 묶으면 호출 횟수와 실수가 줄어든다.

## 5. Context budget

- 컨텍스트 창은 한정되어 있고, **많이 넣을수록 좋은 게 아니다.** 내용이 길어지면 중요한 정보가 묻히고(중간 내용을 잘 못 찾는 lost in the middle 현상), 비용과 속도도 나빠진다. 그래서 컨텍스트를 **"예산"처럼 나눠 쓴다**고 표현한다.

### 보충: 컨텍스트를 아끼는 방법

| 방법 | 설명 |
|---|---|
| **필요할 때만 불러오기 (progressive disclosure)** | 처음엔 목록·요약만 보여 주고 필요할 때 상세를 읽게 한다. skill이 대표적(설명만 먼저 로드, 쓸 때 본문 로드) |
| **도구 결과 줄이기** | 위 4절처럼 도구가 필요한 것만 돌려주게 만든다 |
| **서브 에이전트에 맡기기** | 파일 수십 개를 뒤지는 일은 서브 에이전트가 자기 컨텍스트에서 하고, **결론만** 메인에 돌려준다 |
| **요약·압축(compaction)** | 대화가 길어지면 지난 내용을 요약해서 바꿔 넣는다 |
| **외부 메모리** | 진행 상황·결정 사항을 파일(예: progress.md, TODO)에 적어 두고 필요할 때 다시 읽는다 |
| **안 쓰는 도구 빼기** | 도구 정의도 매 턴 컨텍스트를 차지한다. 쓰지 않는 도구·MCP 서버는 끈다 |

### 요약 요청의 진짜 니즈

- 사용자가 "요약해 줘"라고 할 때 원하는 건 **전문을 고르게 줄인 축약본이 아니라, 전문 중 나에게 중요한 부분**이다.
- 그래서 요약 단계에 **"무엇이 중요한지"를 판단할 맥락**을 같이 넣어 주면 좋다.
  - 예: 사용자의 목적(무엇을 결정하려고 읽는지), 사용자가 이미 아는 것, 역할(개발자/기획자), 이후 단계에서 무엇에 쓰일지.
- 에이전트 내부에서도 마찬가지다. 도구 결과나 긴 대화를 요약할 때 **"다음 단계에서 필요한 정보가 무엇인지"**를 알려 주고 요약시키면, 중요한 정보가 날아가는 일이 줄어든다.

## 6. Hooks: 절대 규칙을 코드로

- **Hook = 에이전트의 특정 시점에 자동으로 실행되는 코드.** 모델의 판단에 맡기지 않고 **반드시 지켜야 하는 방어 규칙**을 코드로 강제한다. Guide(부탁)가 아니라 Sensor/차단기 역할이다.
- Claude Code 기준 대표 hook:

| Hook | 실행 시점 | 할 수 있는 것 | 예시 |
|---|---|---|---|
| **PreToolUse** | 도구 실행 **직전** | 실행을 **막거나**(deny), 허용하거나, 사용자에게 묻게 함. 인자를 고칠 수도 있음 | `rm -rf`, `git push --force`, `.env` 읽기, 운영 DB 접속 차단 |
| **PostToolUse** | 도구 실행 **직후** | 이미 실행된 건 되돌릴 수 없음. 결과를 보고 **판단·후속 조치**를 하거나 모델에게 피드백을 줌 | 파일 수정 후 자동 포맷터·린터 실행, 테스트 실행 후 실패하면 모델에게 알림 |
| UserPromptSubmit | 사용자 입력 직후 | 입력 검사, 맥락 추가 | 프롬프트에 비밀키가 있으면 차단 |
| Stop / SubagentStop | 에이전트가 끝내려 할 때 | 끝내지 못하게 하고 다시 일하게 함 | "테스트가 통과하기 전엔 종료 금지" |
| SessionStart, PreCompact 등 | 세션 시작, 요약 직전 등 | 맥락 주입, 백업 | 시작할 때 현재 브랜치·TODO를 넣어 줌 |

- hook은 `settings.json`에 등록하고, 셸 명령으로 실행된다. 도구 이름·인자가 JSON으로 들어오고, **종료 코드 2**(또는 JSON 응답의 deny 결정)로 막으면 그 이유가 모델에게 전달된다.

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": "./hooks/block-dangerous.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npx prettier --write \"$CLAUDE_FILE_PATHS\"" }] }
    ]
  }
}
```

(예시는 구조를 보여 주기 위한 것. 실제 입력 형식은 공식 문서의 hooks 항목을 확인할 것.)

- 핵심: **"하면 안 되는 일"은 프롬프트에 쓰는 것만으로는 보장이 안 된다.** 반드시 지켜야 하면 hook으로 만든다.

## 7. Validation vs Evaluation, 그리고 Self-verification

| 구분 | 언제 | 무엇을 | 누가 | 예시 |
|---|---|---|---|---|
| **Validation (검증)** | 작업 **직후**, 단계마다 | "형식상·기능상 맞게 됐나" | 주로 코드(계산적) | 빌드 성공, 테스트 통과, JSON 스키마 일치, 파일이 실제로 생성됐는지 |
| **Evaluation (평가)** | 작업이 **끝난 뒤** 전체에 대해 | "목표를 잘 달성했나, 품질이 좋은가" | Evaluator 모델, 사람 | 요구사항 충족도, 코드 품질, 답변의 유용성 점수 |

- Validation은 싸고 빠르니 **자주, 일찍** 돌린다. 여기서 걸러지는 오류를 Evaluation까지 끌고 가면 비싸고, 어디서 틀렸는지 찾기도 어렵다.
- 순서: **작은 단계 → validation → 다음 단계 → validation → … → 마지막에 evaluation.**

### Self-verification (자기 검증)

- 에이전트가 **스스로 결과를 확인하는 단계를 작업 과정에 넣는 것.** 메모에는 제목만 있어서 보충한다.
  - "코드를 고쳤다"로 끝내지 않고 **직접 테스트를 실행해서 통과를 확인**한 뒤 끝낸다.
  - 웹 UI를 만들었다면 **브라우저로 띄워 스크린샷을 보고** 확인한다(Playwright 등).
  - 결과를 보고하기 전에 요구사항 목록을 하나씩 대조한다.
- 주의: 자기 검증은 **자기가 쓴 테스트로 자기를 검사**하는 것이라 한계가 있다. 모델이 테스트를 쉽게 고치거나("테스트를 통과하도록 테스트를 바꿈") 확인을 건너뛰고 "확인했다"고 말하는 경우도 있다. 그래서 중요한 건 **외부 Sensor(hook, 별도 Evaluator)**로 한 번 더 막는다.
- Self-verification이 잘 되려면 하네스가 **검증 수단을 제공**해야 한다: 테스트 실행 명령, 로컬 서버 띄우는 방법, 확인용 스크립트를 지침이나 skill에 적어 둔다.

## 8. 조금씩 만들고 돌려 보기 (점진적 개발)

- 한 번에 많이 만들게 하지 말고, **작게 만들고 → 돌려 보고 → 다시 작게 만들기**를 반복한다.
- 이유:
  - 한 번에 많이 만들면 **오류가 쌓여서**(누적 오류) 어디서 틀렸는지 찾기 어렵다.
  - 긴 작업은 컨텍스트가 넘쳐서 앞부분 결정을 잊는다.
  - 작게 나누면 단계마다 validation을 걸 수 있다.
- 실전 팁: 기능 목록(TODO)을 파일로 만들어 두고 **한 번에 하나씩** 끝낸 뒤 체크하게 한다. 각 단계가 끝날 때마다 커밋하면 문제가 생겼을 때 되돌리기도 쉽다.
- 하네스를 만드는 것 자체도 마찬가지다. 처음부터 거대한 지침·hook·에이전트를 다 만들지 말고, 필요한 걸 하나씩 추가하면서 효과를 확인한다.

## 9. 잘 만든 하네스 공부하기: oh-my-claudecode와 gajae code

### oh-my-claudecode (OMC)

- Claude Code 위에 얹어 쓰는 **오픈소스 멀티 에이전트 오케스트레이션 플러그인**이다(GitHub `Yeachan-Heo/oh-my-claudecode`). 여러 전문 에이전트와 실행 모드를 미리 정의해 두어서, 요청을 주면 알아서 계획·분담·실행·검증까지 한다.
- **에이전트(지침 문서)마다 쓰는 모델이 지정**되어 있다(모델 라우팅).
  - 실제로 일하는 에이전트: 보통 **Sonnet**
  - 설계·계획·어려운 판단: **Opus**
  - 아주 간단한 작업(파일 찾기, 단순 확인): **Haiku**
- Claude Code에서는 서브 에이전트 파일(`.claude/agents/*.md`) 맨 위 frontmatter의 `model:` 항목에 `opus` / `sonnet` / `haiku`를 적어서 이렇게 나눈다.

```markdown
---
name: explorer
description: 코드베이스에서 파일·함수 위치를 빠르게 찾는다
model: haiku
tools: Read, Grep, Glob
---
너는 위치만 찾아서 경로와 한 줄 설명으로 돌려준다. 코드를 수정하지 않는다.
```

- 모델 라우팅의 이유: 비싼 모델을 모든 일에 쓰면 **비용과 속도**가 나빠지고, 싼 모델을 어려운 일에 쓰면 **품질**이 떨어진다. 일의 난이도에 맞춰 나눈다.

### OMC의 한계와 공부법

- OMC는 기능이 많아져서 **너무 무거워졌다.** 처음 공부하기엔 무엇이 핵심인지 보기 어렵다.
- **협업에는 잘 안 맞는다.** 에이전트가 **알아서 다 해 버리기** 때문에, 사람이 중간에 무엇을 왜 했는지 따라가기 어렵고 팀원끼리 작업을 나누거나 리뷰하기 힘들다. (메모의 "다 알아서 하기 때문"을 이렇게 해석했다.)
- 공부 목표는 OMC를 그대로 쓰는 게 아니라 **"지침을 어느 정도 써야 Claude가 잘 알아듣는지" 감을 잡는 것.** 그 감이 오면 공부는 끝난 것이다.

### gajae code (GJC)

- 저장소: [AJin1068/gajae-code](https://github.com/AJin1068/gajae-code) (원본은 `Yeachan-Heo/gajae-code`, 설치 스크립트 주소 기준). OMC를 만든 Yeachan-Heo가 기여자로 올라 있다. 명령어는 `gjc`.
- 수업에서는 "OMC에서 무거운 걸 덜어 낸 것"이라고 설명했는데, 저장소를 보면 **Claude Code 위에 얹는 플러그인이 아니라 독립된 코딩 에이전트 하네스**다. README의 계보 설명(NOTICE.md)은 `oh-my-pi`라는 작은 에이전트 하네스를 뿌리로 든다. 즉 "OMC 코드를 잘라 낸 것"보다는 **같은 사람이 OMC의 교훈을 바탕으로 필수 요소만 남겨 새로 만든 하네스**에 가깝다.
- 여러 회사 모델을 쓸 수 있다. 이미 결제 중인 구독(Claude, Codex, Cursor, Copilot 등)에 `/login`으로 연결해서 API 요금을 따로 내지 않게 하는 게 특징 중 하나다.

#### 필수 요소만 남긴 구성

- 기본 번들은 **스킬 4개 + 역할 에이전트 4개**뿐이다. OMC보다 훨씬 작다.

| 이름 | 역할 |
|---|---|
| `deep-interview` (스킬) | 모호한 요청을 질문으로 구체적인 요구사항으로 바꿈 |
| `ralplan` (스킬) | 코드를 고치기 전에 구현 계획을 세우고 비평 |
| `ultragoal` (스킬) | 실행·수정·검증·증거까지 목표를 추적 |
| `autoresearch` (스킬) | 리서치를 하고 구조화된 판정으로 마무리 |
| `executor` / `architect` / `planner` / `critic` (에이전트) | 구현 / 설계 / 계획 / 읽기 전용 리뷰 |

- 흐름: `deep-interview → ralplan → ultragoal`. **계획 단계는 계획만 쓰고, 사람이 승인하기 전에는 구현을 시작하지 않는다.** OMC가 "다 알아서 해서 협업에 안 좋다"는 문제를 **사람 승인 단계**로 푼 것으로 볼 수 있다.
- 이 구조가 오늘 배운 내용과 그대로 맞물린다: 계획(Guide) → 실행 → **검증과 증거(Sensor)**, 그리고 Generator(`executor`)와 분리된 리뷰어(`critic`).
- 스킬은 Claude Code와 같은 `SKILL.md` 규약을 쓴다. 단, 실행할 때는 `.gjc/skills/`(프로젝트) 또는 `~/.gjc/agent/skills/`(전역)에 있는 것만 로드한다.

#### Token diet (README의 "토큰을 덜 쓰기")

README는 **토큰 비용의 양쪽**, 즉 "같은 토큰을 싸게 쓰기"와 "토큰 자체를 덜 쓰기"를 둘 다 줄인다고 설명한다.

1. **캐시 히트 늘리기 (같은 토큰을 싸게)**
   - 프로바이더별로 프롬프트 캐시 보존 시간(`cacheRetention`)을 조절한다. Anthropic은 기본을 **long(1시간)**으로 둔다. 에이전트 작업은 길어서 **5분짜리 짧은 캐시는 쉽게 깨지기** 때문이다(도구 하나가 오래 걸리면 캐시가 만료되어 다음 호출에서 전부 다시 계산된다).
   - 모델을 고를 때 입력 단가뿐 아니라 **캐시 읽기(`cacheRead`) 단가**가 싼 경로를 우선한다.
   - 캐시가 잘 맞으려면 **프롬프트 앞부분(시스템 프롬프트, 도구 정의)이 매번 똑같아야** 한다. 앞쪽에 날짜나 랜덤 값처럼 자주 바뀌는 내용을 넣으면 캐시가 매번 깨진다. (10/8 캐싱 수업과 이어지는 내용)
2. **컨텍스트 절약 (토큰 자체를 덜)**
   - **코드 파일을 읽으면 기본으로 구조 요약**(어떤 함수·클래스가 있는지)을 돌려주고, 전체 내용은 필요할 때만 따로 요청한다. 위 5절의 progressive disclosure와 같은 원리다.
   - **너무 긴 셸 출력은 잘라서** 보여 주고, 원문은 `artifact://` 참조로 따로 저장한다. 모델은 정말 필요할 때만 그 참조로 원문을 다시 읽는다. 4절 "도구 결과는 짧게"를 하네스 차원에서 강제하는 셈이다.
   - **컴팩션(요약 압축)과 브랜치 요약**으로 긴 세션을 이어 간다. 단, README도 **요약은 손실이 있다(lossy)**고 분명히 적는다. 중요한 세부 사항은 다시 확인해야 한다.
- 정리하면 gajae code의 token diet는 "프롬프트를 짧게 쓰자" 수준이 아니라, **도구가 돌려주는 결과의 크기와 캐시 구조를 하네스가 직접 관리**하는 방식이다.

## 10. 하네스를 만드는 순서와 검증

### 처음엔 Skill부터

- **Skill = 반복적인 작업을 정의해 둔 것.** "이런 일을 할 때는 이 순서로, 이 도구로, 이 형식으로"를 문서로 묶어 둔다.
- Claude Code의 skill은 폴더 안의 `SKILL.md`(필요하면 스크립트·참고 파일 포함)로 만든다. frontmatter의 `name`과 `description`만 평소에 로드되고, 작업이 description과 맞으면 그때 본문을 읽는다. 그래서 **skill을 많이 만들어도 컨텍스트를 거의 차지하지 않는다**(progressive disclosure).

```markdown
---
name: class-note-summary
description: 수업 메모를 받아 틀린 부분 수정, 보충, 주제별 요약을 만들 때 사용
---
1. 메모를 주제별로 나눈다.
2. 틀린 설명은 고치고, 고친 이유를 맨 아래에 따로 적는다.
3. class-notes/YYYY-MM-DD.md로 저장한다.
```

- 왜 skill부터인가: 가장 작고 바로 효과가 보이는 단위다. 자주 하는 일을 skill로 만들고 → 써 보면서 고치고 → 안 지켜지는 규칙은 hook으로, 너무 큰 일은 서브 에이전트로 넓혀 가는 순서가 자연스럽다(8절 "조금씩 만들기").

### 하네스 검증

- **다른 사람에게 공유해서 그 사람 환경에서도 잘 동작하면 잘 만든 하네스다.**
  - 내 컴퓨터에서만 되는 하네스는 내 머릿속 맥락(암묵지)에 기대고 있을 가능성이 크다. 다른 사람이 써도 되면 지침이 **충분히 명시적**이라는 뜻이다.
- 보충: 사람 테스트에 더해, 대표 작업 몇 개를 **평가 세트**로 만들어 하네스를 고칠 때마다 다시 돌려 보면(11/3 trajectory 평가, LLM judge) 바꾼 것이 좋아졌는지 나빠졌는지 확인할 수 있다.

## 11. 한 줄 요약

- 하네스 = 모델 밖의 모든 것(지침, 도구, 컨텍스트, hook, 검증, 모델 배치).
- Guide로 방향을 잡고, **Sensor(테스트·hook·Evaluator)로 최종 보장**. 요즘은 Sensor 쪽에 힘을 준다.
- 에이전트의 핵심은 도구 호출이니 **도구 설계**가 중요하고, 컨텍스트는 **예산**처럼 아껴 쓴다.
- 절대 규칙은 **hook**, 단계마다 **validation**, 끝에 **evaluation**, 그 사이에 **self-verification**.
- 작게 만들고 돌려 보기. 하네스도 **skill부터** 작게 시작한다.

## 원래 메모에서 고친 부분

1. **"하네스 자체가 end to end 에이전트에게 맡기는것"**
   하네스는 "맡기는 행위"가 아니라, 에이전트가 end to end로 일을 해낼 수 있게 **모델을 둘러싼 구조(지침, 도구, 컨텍스트, 검증 등) 전체**를 말한다. 목적(끝까지 맡기기)과 대상(그걸 가능하게 하는 장치)을 구분해서 정리했다.
2. **"evaluator는 Generator와는 다른 모델을 씀"**
   보통 그렇게 하지만 필수는 아니다. 핵심은 **생성한 쪽과 맥락을 분리하는 것**(자기 선호 편향, 잘못된 가정 공유 방지)이라 같은 모델이라도 새 컨텍스트에서 평가하게 하면 된다는 점을 덧붙였다.
3. **"Guide를 완전 듣지 않는 경우가 더 늘어나고(Reasoning 정도가 빡세짐)"**
   방향은 맞다. 이유를 "reasoning이 강해져 지침보다 자기 판단을 우선함", "긴 컨텍스트에서 지침이 묻힘", "Guide는 확률적, Sensor는 결과를 직접 확인"으로 풀어 썼다. Guide가 필요 없어진 건 아니고 **Guide + Sensor 조합**이라는 점도 추가했다.
4. **"preToolUse: 절대 하면 안됨" / "postToolUse: 실행 후 판단 액션"**
   맞다. 이름을 공식 표기 **PreToolUse / PostToolUse**로 맞췄다. PostToolUse는 **이미 실행된 걸 되돌리지 못한다**는 점(그래서 막아야 하는 건 반드시 Pre에서)을 덧붙이고, 다른 hook 종류와 설정 예시를 추가했다.
5. **"[Self-verification]"**
   메모에 제목만 있어서 내용(직접 테스트 실행·화면 확인)과 한계(자기 테스트로 자기 검사)를 보충했다.
6. **"oh my claude code"**
   실제 이름은 **oh-my-claudecode (OMC)**, GitHub `Yeachan-Heo/oh-my-claudecode`로 확인했다. 모델 지정이 Claude Code 서브 에이전트의 `model:` 항목으로 된다는 점을 추가했다.
7. **"Omc는 협업엔 안좋음. 다 알아서 하기 때문"**
   "에이전트가 자율적으로 다 처리해서 사람이 과정을 따라가거나 나눠 리뷰하기 어렵다"는 뜻으로 해석했다. 다른 의미였다면 알려 주면 고치겠다.
8. **"oh my claude code는 이미 너무 무거워져서 … 다 덜어내고 생긴게 gajae code"**
   저장소를 확인해 보니 gajae code는 OMC를 잘라 낸 플러그인이 아니라, **같은 개발자(Yeachan-Heo)가 만든 독립 코딩 에이전트 하네스**(`oh-my-pi` 계보)다. "필수 요소만 남겼다"는 뜻은 맞아서 그대로 두고, 관계를 정확하게 고쳐 적었다. token diet 내용은 README 기준으로 채웠다.
9. **"하네스 검증은 다른 사람에게 공유해서 잘 동작하면 잘 만든것"**
   맞다. 왜 그런지(암묵지에 기대지 않는지 확인)와 평가 세트로 반복 검증하는 방법을 덧붙였다.
10. **표기 통일**: "Omc" → "OMC", "haiku" → "Haiku", "preToolUse/postToolUse" → "PreToolUse/PostToolUse"로 통일했다.
