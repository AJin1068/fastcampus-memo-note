# 수업 정리 (2026-10-05)

## 1. 파이썬 가상환경과 requirements.txt

- 프로젝트에서 쓰는 라이브러리 목록은 보통 **`requirements.txt`** 파일에 적어 둔다.
- `pip install -r requirements.txt` 한 줄로 파일에 적힌 라이브러리를 한 번에 설치한다.
- 버전을 고정하려면 `pandas==2.2.2`처럼 적는다. 버전을 안 적으면 설치 시점의 최신 버전이 깔려서 사람마다 환경이 달라질 수 있다.
- 지금 환경에 깔린 목록을 파일로 뽑을 때는 `pip freeze > requirements.txt`.
- 기본 흐름:
  ```bash
  python -m venv .venv            # 가상환경 생성
  source .venv/bin/activate       # macOS/Linux 활성화 (Windows: .venv\Scripts\activate)
  pip install -r requirements.txt
  ```

## 2. 숨김 파일 (점 파일)

- macOS/Linux에서는 이름이 `.`으로 시작하는 파일·폴더가 숨김 처리된다. 예: `.venv`, `.env`(API 키 같은 비밀값), `.gitignore`.
- `ls`로는 안 보이고 `ls -a`로 봐야 보인다.
- Windows는 이름이 아니라 파일 속성(숨김 속성)으로 숨긴다는 점이 다르다.
- `.env`와 `.venv`는 보통 `.gitignore`에 넣어서 깃에 올라가지 않게 한다.

## 3. Jupyter 커널

- **커널**: 노트북 셀의 코드를 받아서 실제로 실행해 주는, 뒤에서 계속 켜져 있는 파이썬 프로세스.
- 커널이 켜져 있는 동안 변수와 import가 유지되기 때문에, 셀을 위에서부터 순서대로 안 돌려도 값이 남아 있다. 커널을 재시작하면 전부 사라진다.
- 가상환경을 노트북 커널로 쓰려면 그 환경에 `ipykernel`을 깔고 등록해야 한다.
  ```bash
  pip install ipykernel
  python -m ipykernel install --user --name myenv
  ```
  그다음 노트북에서 커널을 `myenv`로 고른다. 라이브러리를 깔았는데 노트북에서 `ModuleNotFoundError`가 나면 대부분 커널이 다른 환경을 가리키고 있는 경우다.

## 4. 워크플로우 vs 에이전트

- 둘 다 안에서 LLM을 쓴다. 차이는 **"다음에 뭘 할지"를 누가 정하느냐**다.
  - **워크플로우**: 사람이 코드로 정해 둔 순서(1단계 → 2단계 → 분기)를 따라가고, LLM은 각 단계의 작업만 수행한다.
  - **에이전트**: LLM이 상황을 보고 어떤 도구를 쓸지, 몇 번 반복할지, 언제 끝낼지를 스스로 결정한다(자율성).
- 그래서 작업 순서가 예측 가능하면 워크플로우가 싸고 안정적이고, 단계를 미리 정할 수 없는 열린 문제일 때 에이전트가 낫다.

## 5. 멀티 에이전트와 오케스트레이션

- 멀티 에이전트는 각 에이전트가 **자기만의 컨텍스트**를 따로 가지고 돌아간다. 그래서 정보 전달이 끊기기 쉽고, 토큰 비용이 커지고, 디버깅이 어렵다.
- 결론: 꼭 필요한 게 아니면 **단일 에이전트로 먼저** 만들고, 한계가 보일 때 나눈다.
- **오케스트레이션(오케스트레이터-워커)** 구조에서는 작업을 어떻게 쪼개고 누구에게 맡길지를 사람이 아니라 오케스트레이터 LLM이 정한다.
  - 다만 사람이 코드로 순서를 정해 놓은 "워크플로우형 오케스트레이션"도 있으니, LLM이 정하는 쪽은 에이전트형이라고 구분해 두면 정확하다.

### 팀장(Supervisor) 패턴

- 팀장 에이전트가 일을 나눠서 워커들에게 맡기고 결과를 모은다.
- 왜 워커를 그냥 tool로 두지 않나?
  - **tool**: 정해진 입력을 받아 정해진 일을 하는 함수. 스스로 판단하지 못한다.
  - **LLM 워커(서브 에이전트)**: 자기 컨텍스트와 도구를 갖고 중간에 판단(decision)을 내릴 수 있다.
  - 곁가지 작업(사이드 워킹)에 복잡한 판단이 필요하면 함수만으로는 부족해서, 거기에 LLM을 붙여 진짜 "일하는 사람"으로 돌린다.
- 덤으로 팀장의 컨텍스트가 워커의 세부 작업 내용으로 꽉 차지 않는다는 장점도 있다.

## 6. Tool Calling (함수 호출)

- tool을 정의할 때 `name`, `description`, `parameters`(JSON Schema)를 적는다.
- LLM은 **description을 읽고** 어떤 tool을 쓸지 고른다. 그래서 description이 가장 중요하다. 각 파라미터의 description도 LLM이 값을 채울 때 보니 같이 신경 써야 한다.
- **LLM은 함수를 직접 실행하지 않는다.** "이 함수를 이 인자로 불러줘"라고 요청만 하고, 실행은 내 코드가 한다.
- OpenAI Chat Completions 기준 응답 모양:
  - `message.content`가 `None`(비어 있음)
  - `message.tool_calls`에 호출할 함수 이름과 인자(JSON 문자열)가 들어옴
  - `finish_reason`이 `"tool_calls"`
  - (Claude API는 `content` 안에 `tool_use` 블록이 오고 `stop_reason`이 `"tool_use"`. 텍스트가 같이 올 수도 있다.)
- 전체 흐름:
  1. 사용자 메시지 + tool 정의를 보냄
  2. 모델이 `tool_calls`로 호출 요청
  3. 내 코드가 함수를 실행
  4. 결과를 `role: "tool"` 메시지(해당 `tool_call_id` 포함)로 대화에 붙여 다시 보냄
  5. 모델이 결과를 보고 최종 답변(또는 다음 tool 호출)

### 함수 실행 중 에러가 나면

- 에러를 숨기거나 프로그램을 멈추지 말고, **에러 내용을 tool 결과로 모델에게 돌려줘야** 한다. 예: `{"error": "city 'Seuol' not found"}`.
- 그래야 모델이 인자를 고쳐서 다시 부르거나, 사용자에게 상황을 설명할 수 있다.
- 모델이 요청한 `tool_call_id`마다 결과 메시지가 꼭 하나씩 있어야 한다. 빠뜨리면 다음 API 요청이 에러로 거부된다.
- (Claude API에서는 `tool_result` 블록에 `is_error: true`를 붙인다.)

## 7. RAG와 청킹(Chunking)

- 긴 문서(예: 가이드북)를 그대로 LLM에 넣을 수 없으니
  1. 문서를 조각(청크)으로 자르고
  2. 각 청크를 임베딩해서 저장하고
  3. 질문이 오면 유사도 검색으로 상위 k개만 골라
  4. 질문과 함께 LLM에 보낸다.
- **청크 크기는 너무 길어도, 너무 짧아도 안 좋다.**
  - 너무 길면: 한 청크에 여러 주제가 섞여서 임베딩이 흐려지고 검색 정확도가 떨어진다. 질문과 상관없는 내용이 같이 들어가 답이 엉뚱해지고 비용도 늘어난다.
  - 너무 짧으면: 문장이 중간에 잘려 앞뒤 맥락이 사라지고, 정작 답에 필요한 정보가 빠진다. 이것도 할루시네이션 원인이 된다.
- 실무 기본값: 수백 토큰 단위로 자르고, 앞뒤 청크를 10~20% 정도 겹치게(overlap) 한 뒤, 실제 질문으로 테스트하며 조정한다.
- 가능하면 글자 수로 무작정 자르기보다 문단·제목 단위로 자르는 게 좋다.

## 8. 에이전트 개발 도구 선택

선생님이 말씀하신 3가지 분류:

| 방식 | 예시 | 특징 |
|---|---|---|
| 노코드 | n8n, Dify 등 | 화면에서 블록을 연결해 빠르게 만듦. 복잡한 로직엔 한계 |
| SDK 직접 사용 | OpenAI SDK | 가장 자유롭지만 루프·상태 관리 등을 직접 다 짜야 함 |
| 프레임워크 | LangGraph | 상태와 흐름을 그래프로 관리. 멀티 에이전트·분기 구성이 쉬움 |

- 선생님 의견으로는 SDK를 직접 쓰는 경우는 상대적으로 적은 편. (어느 쪽을 쓰든 내부에서는 위의 tool calling 원리가 똑같이 돌아가니, 원리를 이해해 두면 도구가 바뀌어도 응용할 수 있다.)

## 9. 선생님 꿀팁: 역할별로 AI 나눠 쓰기

- **기획+설계 / 코더 / 검증** 세 역할을 분리한다.
- 기획+설계와 검증은 프로젝트 폴더를 웹 버전 Claude에 가져와(import) 전체를 보면서 진행한다.
- 코더 역할은 IDE 안에서 진행한다.
- 만든 사람과 검증하는 사람을 분리하면 자기가 짠 코드를 스스로 봐줄 때 생기는 맹점이 줄어든다. 수업 중 배운 멀티 에이전트 역할 분리를 사람의 작업 방식에 적용한 셈이다.

## 원래 메모에서 고친 부분

1. **`requirement.txt` → `requirements.txt`**
   명령어(`pip install -r requirements.txt`)와 파일 이름이 다르게 적혀 있었다. 관례상 이름은 끝에 s가 붙은 `requirements.txt`다.
2. **"숨김 파일 앞에 .을 붙임"**
   macOS/Linux에서만 맞는 규칙이다. Windows는 파일 속성으로 숨긴다.
3. **"llm은 그냥 워크플로우 로직을 따라갈 뿐"**
   비교 대상이 LLM vs 에이전트라기보다 **워크플로우 vs 에이전트**다. 에이전트도 안에서 LLM이 판단하는 구조라서, 차이는 흐름을 코드가 정하느냐 LLM이 정하느냐에 있다.
4. **"멀티 에이전트는 배타적으로 돌아감"**
   에이전트끼리 동시에(병렬로) 돌 수 있으니 "배타적"은 정확하지 않다. 각자 **컨텍스트가 분리**되어 있어서 정보 공유가 어렵고, 비용과 복잡도가 커진다는 게 정확한 이유다. 단일 에이전트를 먼저 쓰라는 결론은 맞다.
5. **"orchestration 내부 decision은 llm이 정함"**
   에이전트형 오케스트레이터에 해당하는 설명이다. 코드로 순서를 고정한 워크플로우형 오케스트레이션에서는 사람이 정한다.
6. **"가장 중요한 attribute는 description"**
   맞는 말이지만 파라미터별 description과 schema도 LLM이 인자를 채울 때 쓰니 함께 중요하다. 또 `content`가 None으로 오는 건 OpenAI 방식 기준이다.
7. **"청킹은 짧게 하는 게 좋다"**
   너무 짧아도 맥락이 끊겨 문제가 된다. 적당한 크기와 overlap을 정하고 테스트로 맞추는 게 정확하다. 할루시네이션도 "길어서"라기보다 관련 없는 내용이 섞이거나 필요한 정보가 빠질 때 생긴다.
8. **"에러나면 api로 알려줘야함"**
   따로 알리는 API가 있는 게 아니라, 다음 요청의 대화 메시지에 **tool 결과로 에러 내용을 넣어서** 보내는 방식이다.
