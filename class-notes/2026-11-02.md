## 1. 에이전트는 왜 만들기 어려운가

### loop를 많이 돌린다고 성공률이 올라가지 않는다

- 에이전트는 여러 step을 이어서 실행한다. 각 step이 성공할 확률을 p, step 수를 n이라고 하면 **전체 성공률은 대략 pⁿ**이다. step마다 실수가 **곱해지며 쌓이기(compounding error)** 때문이다.
  - 예: 한 step 성공률이 95%여도 10 step이면 0.95¹⁰ ≈ **60%**, 20 step이면 ≈ **36%**까지 떨어진다.
- 특히 **초반 step에서 한 번 틀리면** 그 뒤 step들은 틀린 결과를 입력으로 받는다. 그래서 loop가 돌수록 오류가 커지고, 엉뚱한 방향으로 계속 가거나 같은 행동을 반복하기도 한다.
- 그래서 설계 원칙은 두 가지다.
  1. **한 step의 성공 확률을 최대한 높인다.** 프롬프트를 명확히, 도구 설명을 구체적으로, 출력 형식을 고정(structured output)한다.
  2. **step 수 자체를 줄인다.** 코드로 확실히 처리할 수 있는 건 LLM에 맡기지 않고, 여러 단계를 한 번에 처리하는 도구를 만들고, `max_iterations`(LangGraph는 `recursion_limit`)로 무한 루프를 막는다.
- 참고: Anthropic의 "Building effective agents"도 **가능하면 단순한 workflow(정해진 단계)로 해결하고, 꼭 필요할 때만 자율 에이전트를 쓰라**고 권한다.

## 2. Reflexion (회고)

### Reflexion이란?

- Shinn 외(2023) 논문 "Reflexion: Language Agents with Verbal Reinforcement Learning". 에이전트가 실패하면 **왜 실패했는지 말(텍스트)로 반성문을 쓰고, 그걸 기억해 두었다가 다음 시도에 참고**하게 하는 방법이다. 모델 가중치를 바꾸지 않고 "말로 하는 강화학습"을 한다고 해서 verbal reinforcement라고 부른다.
- 세 가지 역할로 나뉜다.
  - **Actor**: 실제로 행동(답 생성, 도구 호출, 코드 작성)한다. 보통 ReAct나 CoT 방식으로 동작한다.
  - **Evaluator**: Actor의 결과가 성공인지 실패인지 점수를 매긴다. 규칙(정답 일치), 단위 테스트 통과 여부, 또는 LLM 판정을 쓴다.
  - **Self-Reflection**: 실패한 시도의 기록(trajectory)과 평가 결과를 읽고 "무엇이 잘못됐고 다음엔 어떻게 해야 하는지"를 써서 **메모리(long-term memory)에 저장**한다.
- 흐름: Actor 시도 → Evaluator 평가 → 실패면 Self-Reflection이 반성문 작성 → 반성문을 Actor 프롬프트에 붙여 다시 시도 → 성공하거나 최대 횟수에 도달할 때까지 반복.

### 어느 역할에 가장 좋은 모델을 쓸까

- 선생님 의견: **Self-Reflection에 가장 좋은 모델**을 쓴다.
  - Self-Reflection은 **긴 입력**(시도 전체 기록 + 평가)을 읽고 실패 원인을 진단해야 해서 가장 어려운 일이다. 그리고 그 결과가 메모리에 저장돼 **다음 시도 전체에 영향**을 준다. 반성문이 틀리면 다음 시도도 틀린 방향으로 간다.
  - Actor는 한 번에 내는 출력(행동 하나, 짧은 답)이 비교적 짧다.
- 단, **task에 따라 달라진다.** 예를 들어 코드 생성처럼 Actor가 길고 어려운 출력을 내야 하는 일이면 Actor에 좋은 모델이 필요하다. 평가 기준이 애매해서 Evaluator가 LLM 판정이면 Evaluator 품질도 중요하다.
- 참고: 메모리에 반성문이 계속 쌓이면 컨텍스트가 길어지므로, 논문에서는 **최근 1~3개만** 남긴다.

### 구현 방법

- LangChain의 기본 에이전트(`AgentExecutor`, `create_agent` 등)는 "Actor → 평가 → 반성 → 재시도" 같은 구조를 기본 제공하지 않는다.
- 그래서 직접 만든다.
  - **파이썬 코드에서 `for`/`while` + `if`로** 시도 → 평가 → 실패면 반성 → 재시도 루프를 짠다.
  - **LangGraph**로 actor·evaluator·reflection을 각각 노드로 만들고, 평가 결과에 따라 **conditional edge**로 "종료" 또는 "reflection → actor"로 보낸다. LangGraph 공식 튜토리얼에도 Reflexion 예제가 있다.

## 3. CoT-Self-Consistency와 Tree of Thoughts

### CoT-Self-Consistency (CoT-SC)

- Wang 외(2022). 같은 질문에 대해 **CoT(Chain-of-Thought, 단계별 추론)를 여러 번 샘플링**한다(temperature를 높여 서로 다른 추론 경로가 나오게 함).
- 각 추론 경로의 **최종 답만 모아서 가장 많이 나온 답(majority vote, 다수결)**을 고른다. 추론 과정이 달라도 같은 답에 많이 도달하면 그 답이 맞을 가능성이 높다는 생각이다.
- 단점: 경로를 끝까지 다 만들어야 하므로 **호출 수만큼 비용이 든다.** 그리고 중간 단계를 평가하지 않아서, 처음부터 틀린 경로도 끝까지 돌린다.

### Tree of Thoughts (ToT)

- Yao 외(2023). 추론을 **생각(thought) 단위로 쪼개 나무(tree) 형태로 탐색**한다.
  1. 각 단계에서 다음 생각 후보를 여러 개 만든다.
  2. LLM이 **각 후보(중간 상태)가 가망 있는지 평가**한다.
  3. 가망 있는 가지만 남기고 나머지는 **잘라낸다(pruning)**. 막히면 이전 단계로 **되돌아간다(backtracking)**.
  4. 탐색은 BFS(너비 우선)나 DFS(깊이 우선)로 한다.
- CoT-SC와의 차이: CoT-SC는 "끝까지 여러 개 돌리고 마지막에 투표", ToT는 **"중간중간 평가해서 좋은 가지만 골라 나아감"**이다.
- 주의: ToT가 꼭 호출 수를 줄여 주는 건 아니다. 후보 생성 + 평가 호출이 많아서 **오히려 비용이 더 들 수 있다.** 핵심 장점은 비용 절감보다 **중간 평가와 되돌아가기로 어려운 문제(퍼즐, 계획)를 더 잘 푼다**는 점이다.

## 4. 에이전트 구축 시 모델 선택

### reasoning effort는 끄거나 최소로

- 선생님 의견: 에이전트를 만들 때는 **reasoning(추론 모드)을 꺼야 한다.**
  - 이유: 내가 설계한 **step by step 흐름대로** 실행돼야 하는데, 모델이 스스로 길게 추론하면 단계를 건너뛰거나 합치거나 다른 계획을 세워서 **흐름을 제어하기 어렵다.** 응답이 느려지고 토큰 비용도 늘어난다.
  - 설정 예: OpenAI는 `reasoning_effort`(`minimal`/`low`/`medium`/`high`), Claude는 extended thinking을 켜지 않으면 된다. 모델에 따라 **완전히 끌 수 없고 최소로만 낮출 수 있는** 경우도 있다.
- 보충: "무조건"은 **흐름을 내가 정하는 workflow형 에이전트** 기준이다. 모델이 스스로 계획을 세워야 하는 자율 에이전트(코딩 에이전트 등)는 오히려 reasoning이 성능을 높이기도 한다.

### 연구할 땐 저가 모델을 쓴다

- 모델이 좋아질수록 reasoning이 고도화돼서, 모델이 **혼자서도 잘 해 버린다.** 그러면 내가 만든 에이전트 구조(프롬프트, 단계 설계, reflexion 등)가 성능을 얼마나 올렸는지 **효과를 구분하기 어렵다.**
- 그래서 연구에서 에이전트 방법론을 실험할 때는 **저가(작은) 모델**을 많이 쓴다. 비용이 싸서 실험을 많이 돌릴 수 있다는 장점도 있다.

## 5. LangChain 실습 팁

### RecursiveCharacterTextSplitter의 overlap

- `chunk_overlap`은 **`chunk_size`의 10% 정도**가 적당하다. (보통 10~20%를 많이 쓴다.) 예: `chunk_size=1000, chunk_overlap=100`.
- overlap은 문장이 청크 경계에서 잘려 의미가 끊기는 걸 막아 준다. 너무 크면 중복이 많아져 저장 공간과 검색 결과의 중복이 늘어난다.
- 참고: 기본 `length_function`은 `len`이라서 **글자 수 기준**이다. 토큰 기준으로 자르려면 `RecursiveCharacterTextSplitter.from_tiktoken_encoder(...)`를 쓴다. (10/7 수업 청킹 참고)

### Chroma.from_documents에서 ids를 지정하자

- `Chroma.from_documents(docs, embedding, collection_name="my_col", persist_directory=...)`처럼 **같은 collection 이름으로 다시 실행하면** 기존 collection에 문서가 **또 추가된다.** ids를 안 주면 매번 새로운 랜덤 UUID가 붙어서 같은 내용이 다른 문서로 취급되기 때문이다.
- 그 결과 top-k 검색 때 **똑같은 청크가 여러 개** 뽑혀 나온다. Jupyter에서 셀을 여러 번 실행하거나, `persist_directory`에 저장한 DB에 다시 적재할 때 자주 생긴다.
- 해결: **청크마다 고정된 id를 직접 지정**한다. `langchain-chroma`는 같은 id가 들어오면 새로 추가하지 않고 **덮어쓴다(upsert).**

```python
import hashlib
ids = [hashlib.md5(d.page_content.encode()).hexdigest() for d in docs]
# 또는 f"{d.metadata['source']}-{i}" 처럼 출처 + 순번
db = Chroma.from_documents(docs, embedding, collection_name="my_col", ids=ids)
```

- 주의: 내용 해시를 id로 쓰면 **완전히 같은 내용의 청크가 두 개 있을 때 id가 겹쳐** 에러가 나거나 하나만 남는다. 출처 + 순번을 섞어 쓰면 안전하다.
- 다른 방법: 다시 적재하기 전에 `db.delete_collection()`으로 지우고 새로 만든다.

### LangChain vs LangGraph

- LangChain의 에이전트(`create_agent`, 예전 `AgentExecutor`)는 **ReAct(Reasoning + Acting) 루프를 내부에서 알아서 돌린다.** "생각 → 도구 호출 → 결과 관찰 → 다시 생각"을 반복하는데, 이 반복이 감춰져 있어서 **각 step을 세세하게 제어하기 어렵다.**
- 그래서 **LangGraph**를 쓴다. 노드(할 일)와 엣지(다음에 어디로 갈지), 상태(state)를 내가 직접 정의하므로 step 순서, 분기, 반복 횟수, 중간에 사람 확인 넣기(human-in-the-loop) 등을 모두 제어할 수 있다.
- 참고: LangChain 1.0의 `create_agent`는 내부적으로 LangGraph 위에서 만들어져 있다. 즉 "편하게 쓰는 완성품"이 LangChain 에이전트이고, "직접 조립하는 부품"이 LangGraph다.

## 원래 메모에서 고친 부분

1. **"agent loop를 많이 돌린다고 성공률이 높아지는건 아니다 ... 누적으로 낮아진다"**
   맞다. **step 성공률의 곱(pⁿ)**으로 떨어진다는 설명과 계산 예(0.95¹⁰ ≈ 60%)를 붙였다. "step을 낮추는" → "**step 수를 줄이는**"으로 풀어 썼다.
2. **"[reflexion; 회고]"**
   논문 정보(Shinn 외, 2023)와 Actor / Evaluator / Self-Reflection 각 역할, 전체 흐름을 추가했다.
3. **"self-reflection는 입출력이 길고 긴걸 저장해야함"**
   Self-Reflection이 **긴 시도 기록을 입력으로 읽고**, 반성문을 **메모리에 저장**해 다음 시도에 쓴다는 뜻으로 정리했다. 가장 좋은 모델을 쓰는 이유로 "반성문이 다음 시도 전체에 영향을 준다"를 덧붙였다.
4. **"langchain으론 안됨"**
   LangChain을 아예 못 쓴다는 뜻이 아니라, **LangChain 기본 에이전트가 reflexion 구조를 제공하지 않아서** 코드(if/while)나 LangGraph로 직접 짜야 한다는 뜻으로 고쳤다.
5. **"majority vode", "Cot", "cot-self consistency"**
   **majority vote**(다수결), **CoT**, **CoT-Self-Consistency**로 고쳤다. "majority vote인 애들만 뽑는" → 여러 경로의 **최종 답 중 가장 많이 나온 답 하나를 고르는** 것으로 고쳤다.
6. **"굳이 이렇게 많이 돌릴 필요 있나, tree로 필요한것만 선택하자 라고 한게 tree of thought"**
   "필요한 가지만 고른다"는 맞지만, ToT의 핵심은 **중간 단계 평가 + 가지치기 + 되돌아가기**다. 호출 수가 오히려 늘 수도 있다는 점을 덧붙였다. 정식 이름은 **Tree of Thoughts**(복수형).
7. **"reasoning effort 무조건 꺼야함"**
   선생님 의견이라 그대로 두고, **workflow형 에이전트 기준**이라는 점과 모델에 따라 완전히 끌 수 없고 최소로만 낮출 수 있다는 점을 보충했다.
8. **"보통 연구할때 에이전트를 만들땐 저가 모델을 씀"**
   이유(좋은 모델은 혼자서도 잘 해서 **에이전트 구조의 효과를 구분하기 어려움**, 실험 비용)를 붙였다.
9. **"Overlap설정할땐 chunk사이즈의 10% 정도"**
   맞다. 흔히 10~20%를 쓴다는 점과 기본이 글자 수 기준이라는 점을 추가했다.
10. **"ids 안쓰면 동일한 collection name별로 중복 적재되기 떄문에"**
    맞다. 원인이 **랜덤 UUID**라는 점, 고정 id를 주면 **upsert(덮어쓰기)**된다는 점, 코드 예와 주의점을 추가했다. 오타 "떄문에" → "때문에".
11. **"langchain은 저절로 React를 내부에서 수행하기 떄문에"**
    **ReAct**(Reasoning + Acting)다. 자바스크립트 라이브러리 React와 헷갈리지 않게 표기를 고쳤다. 오타 "떄문에" → "때문에".
