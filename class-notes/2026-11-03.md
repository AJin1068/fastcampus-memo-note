## 1. 데이터 분석을 에이전트에 맡길 때: PythonAstREPLTool

### DataFrame을 그대로 넘기면 왜 틀리나

- pandas DataFrame을 문자열로 바꿔(`df.to_string()` 등) 프롬프트에 넣으면, LLM이 **표를 눈으로 읽고 머릿속으로 계산**하게 된다. LLM은 합계, 평균, 필터링 같은 계산을 정확하게 하지 못해서 **그럴듯하지만 틀린 숫자**를 내기 쉽다.
- 데이터가 크면 **컨텍스트 길이를 넘거나** 중간이 잘려서 일부만 보고 답하기도 한다. 토큰 비용도 많이 든다.

### PythonAstREPLTool을 쓰는 방식

- LLM에게 데이터 자체가 아니라 **"데이터를 다루는 파이썬 코드를 실행할 수 있는 도구"**를 준다. LLM은 `df['매출'].mean()` 같은 **코드를 작성**하고, 실제 계산은 **파이썬이 정확하게** 한다. LLM은 그 결과를 보고 답을 정리한다.
- `PythonAstREPLTool(locals={"df": df})`처럼 DataFrame을 도구 안의 변수로 넣어 두면, LLM은 `df`라는 이름으로 접근만 하면 된다. 보통 프롬프트에는 `df.head()` 정도와 컬럼 정보만 보여 줘서 구조를 알려 준다.
- `langchain_experimental`의 `create_pandas_dataframe_agent`가 내부적으로 이 도구를 쓴다.
- 주의: LLM이 만든 코드를 **그대로 실행**하는 도구라서 보안 위험이 있다. 그래서 `create_pandas_dataframe_agent`는 `allow_dangerous_code=True`를 직접 켜야 동작한다. 실서비스에서는 샌드박스(격리된 환경)에서 실행하는 게 안전하다.

## 2. 슈퍼바이저(Supervisor) 에이전트 구조

### 구조

- **Supervisor 에이전트**가 사용자 요청을 받아 어떤 **sub agent(작업 담당 에이전트)**에게 일을 맡길지 정하고, 결과를 받아 다음 담당자를 정하거나 최종 답을 만든다.
  - 예: 사용자 질문 → Supervisor → (데이터 검색 agent → 분석 agent → 보고서 작성 agent) → Supervisor가 최종 답.
- LangGraph에서는 Supervisor를 하나의 노드로 두고, 그 출력(다음 담당자 이름)에 따라 **conditional edge**로 sub agent 노드에 보낸다. `langgraph-supervisor` 패키지의 `create_supervisor(agents=[...], model=..., prompt=...)`로 빠르게 만들 수도 있다.

### 보충: conditional edge는 언제 쓰나

- LangGraph의 엣지는 두 종류다.
  - **일반 edge** (`add_edge("A", "B")`): A가 끝나면 **항상** B로 간다. 순서가 고정된 단계에 쓴다.
  - **conditional edge** (`add_conditional_edges("A", 판단함수, {...})`): A가 끝난 뒤 **현재 state를 보고 다음 노드를 그때그때 고른다.** 판단 함수가 다음 노드 이름(또는 `END`)을 돌려준다.
- 한마디로 **"다음에 어디로 갈지가 실행 결과에 따라 달라질 때"** 쓴다. 대표적인 경우는 다음과 같다.

| 용도 | 언제 | 예시 |
|---|---|---|
| **라우팅(분기)** | 입력이나 판단에 따라 담당자가 달라질 때 | Supervisor가 고른 이름에 따라 검색/분석/작성 agent로 보냄. 질문 종류(일반 대화 vs 데이터 질문)에 따라 다른 경로로 보냄 |
| **도구 호출 여부 확인 (ReAct 루프)** | LLM이 도구를 부를지, 답을 끝낼지 모를 때 | LLM 응답에 `tool_calls`가 있으면 `tools` 노드로, 없으면 `END`. LangGraph의 `tools_condition`이 이 역할을 하는 기본 함수다 |
| **반복/재시도 (loop)** | 결과가 기준을 못 넘으면 다시 해야 할 때 | 11/2 Reflexion: evaluator가 실패면 `reflection → actor`로, 성공이면 `END`. 10/7 CRAG: 검색 문서가 관련 없으면 질문 재작성·웹 검색으로 |
| **종료 조건** | 무한 루프를 막아야 할 때 | 시도 횟수가 `max_retries`에 도달하면 성공 여부와 상관없이 `END` |
| **예외·실패 처리 (fallback)** | 도구 오류나 빈 결과가 나올 수 있을 때 | API 오류면 대체 도구 노드로, 결과가 비면 사용자에게 다시 묻는 노드로 |
| **사람 확인 (human-in-the-loop)** | 위험하거나 비싼 작업 전에 승인이 필요할 때 | 결제·삭제 같은 작업이면 승인 노드로, 아니면 바로 실행 노드로 |

```python
from langgraph.graph import StateGraph, END

def route_after_supervisor(state):
    # Supervisor가 state에 적어 둔 다음 담당자를 읽는다
    if state["retries"] >= 3:          # 종료 조건
        return END
    return state["next"]               # "search" / "analyze" / "write" / "FINISH"

graph.add_conditional_edges(
    "supervisor",
    route_after_supervisor,
    {"search": "search_agent", "analyze": "analyze_agent",
     "write": "write_agent", "FINISH": END, END: END},
)
# sub agent는 일이 끝나면 항상 supervisor로 돌아온다 → 일반 edge
graph.add_edge("search_agent", "supervisor")
```

- Supervisor 구조는 "**supervisor → (conditional edge) → sub agent → (일반 edge) → supervisor**"가 반복되는 모양이다. 갈 곳을 고르는 쪽만 conditional, 돌아오는 쪽은 일반 edge다.
- 팁: 판단 함수는 **LLM을 다시 부르지 말고 state 값만 보고 빠르게 결정**하는 게 좋다. 판단은 앞 노드(Supervisor)에서 structured output으로 `next` 값을 정해 두고, 엣지는 그 값을 읽기만 한다. 그래야 흐름이 예측 가능하고 디버깅이 쉽다.
- 참고: 최신 LangGraph에서는 노드가 `Command(goto="search_agent")`를 돌려줘서 노드 안에서 바로 다음 노드를 정하는 방법도 있다. 역할은 conditional edge와 같다.

### 핵심은 Supervisor system prompt의 순서 지정

- Supervisor 프롬프트에 **어떤 순서로 어떤 sub agent를 호출할지**(예: "반드시 검색 → 분석 → 작성 순서로 진행", "분석 결과가 없으면 작성 agent를 부르지 말 것")와 **언제 끝낼지**를 명확히 적어야 한다.
- 이게 없으면 Supervisor가 순서를 건너뛰거나(검색 전에 분석 agent 호출), 같은 agent를 반복 호출하거나, 끝내지 않고 계속 돌아서 **sub agent의 task가 꼬인다.**
- 11/2 수업의 **누적 오류(pⁿ)**와 연결된다. 멀티 에이전트는 호출 단계가 더 많으니 순서가 한 번 틀어지면 뒤가 전부 틀어진다. 순서가 항상 고정이라면 아예 Supervisor 없이 **LangGraph 엣지로 순서를 코드에 고정**하는 것도 방법이다.

### sub agent의 도구 설명은 sub agent 프롬프트에

- 각 sub agent가 쓰는 **도구의 역할과 사용 시점**은 그 **sub agent의 프롬프트**에 미리 적어 두는 게 맞다. (도구 함수의 docstring/description도 구체적으로 쓴다.)
- 역할 분리: **Supervisor는 "어떤 sub agent가 무슨 일을 하는지"만** 알면 되고, **도구를 어떻게 쓰는지는 sub agent가** 안다. Supervisor 프롬프트에 모든 도구 설명을 몰아넣으면 프롬프트가 길어지고 Supervisor가 직접 도구를 쓰려 하는 등 헷갈린다.

## 3. 멀티 에이전트의 로깅

- 에이전트가 많을수록 **어느 agent가 언제 무엇을 입력받아 무엇을 했는지** 기록해야 문제가 생긴 지점을 찾을 수 있다.
- 로그가 너무 많으니 **tag(태그)나 metadata**를 붙여서 걸러 본다.
  - LangChain/LangGraph는 실행할 때 `config={"tags": ["analysis_agent"], "metadata": {"user_id": "..."}, "run_name": "..."}`처럼 태그를 붙일 수 있다.
  - **LangSmith**를 연결하면 이 태그로 실행 기록(trace)을 필터링해서, agent별로 입력·출력·도구 호출·토큰·시간을 볼 수 있다. (Langfuse 같은 다른 도구도 비슷하게 지원)

## 4. 에이전트 평가 (Evaluation)

### 먼저 정할 것: 무엇을, 무엇을 기준으로

- 평가 대상(최종 답? 중간 과정? 도구 선택?)과 기준(정답 일치, 사실성, 형식, 비용, 속도 등)을 먼저 정해야 한다. 기준 없이 "잘했나"를 물으면 평가 결과를 믿을 수 없다.
- 에이전트 평가는 보통 세 가지로 나눈다.
  1. **최종 응답 평가(final response)**: 답이 맞았나.
  2. **단일 step 평가(single step)**: 특정 단계에서 올바른 도구/인자를 골랐나.
  3. **trajectory 평가**: 전체 과정(어떤 도구를 어떤 순서로 썼나)이 맞았나.

### LLM-as-a-judge의 한계 (10/7 수업 참고)

- LLM judge에게 **1~10점 같은 정량 점수**를 매기게 하면 신뢰도가 애매하다.
  - 같은 답에도 실행할 때마다 점수가 흔들리고, 점수 기준(7점과 8점의 차이)이 모호하다.
  - 긴 답을 더 좋게 보는 경향(verbosity bias), 먼저 나온 답을 선호하는 경향(position bias), 자기 모델 답을 선호하는 경향(self-preference) 등이 있다.
  - 특히 **정답이나 기준 점수가 없는 데이터**는 judge 점수가 맞는지 확인할 방법이 없어서 의미가 없을 수 있다.
- 대안: 점수 대신 **통과/실패(binary)**나 **두 답 비교(pairwise)**로 묻기, 항목별 **체크리스트(rubric)** 주기, 사람이 평가한 일부 데이터와 judge 결과가 얼마나 일치하는지 먼저 확인하기.

### judge에게 "답을 만들라" 하지 말고 "검증하라"

- judge에게 **정답을 직접 만들게 한 뒤 비교**시키면, 모델이 정답을 대충 만들어서 그 기준 자체가 틀릴 수 있다. 그러면 평가가 더 나빠진다.
- 비슷해 보여도 **주어진 답이 맞는지 근거를 하나씩 따져(논증) 검증**하게 하는 게 낫다. 예: "답의 각 주장을 문서 근거와 대조하고, 근거를 먼저 쓴 다음 마지막에 PASS/FAIL을 내라."
- 이유를 먼저 쓰고 판정을 마지막에 내게 하면(CoT 후 판정) 판정이 더 안정적이다.

### Trajectory 평가

- 최종 답이 맞는지 판단하기 어려울 때, **과정이라도 맞는지** 본다. 사람이 생각한 풀이 흐름(예: 검색 → 계산 → 작성)을 **기준 trajectory**로 만들어 두고, 에이전트가 **같은 흐름으로 도구를 호출했는지** 비교한다.
- 비교 방식(LangChain `agentevals` 패키지의 `create_trajectory_match_evaluator` 기준):
  - **strict**: 도구 호출 순서까지 똑같아야 통과.
  - **unordered**: 같은 도구들을 호출했으면 순서는 상관없음.
  - **subset / superset**: 기준보다 적게(불필요한 호출 없음) / 기준을 모두 포함하면 통과.
  - 정해진 정답 흐름이 애매하면 **LLM judge에게 trajectory를 보여 주고 합리적인지** 평가하게 할 수도 있다.
- 장점: 어느 단계에서 틀렸는지 알 수 있어 디버깅에 좋다. 한계: 사람이 생각하지 못한 **다른 올바른 경로**를 틀렸다고 볼 수 있다.

## 원래 메모에서 고친 부분

1. **"pandas dataframe 자체를 넘기면 Llm이 틀릴 수도 있기 떄문에 PythonAstREPLTool를 사용해서 넘김"**
   DataFrame을 도구로 "넘기는" 게 아니라, **DataFrame을 도구 안 변수로 두고 LLM은 코드만 작성, 계산은 파이썬이 실행**하는 구조라는 점을 분명히 했다. 틀리는 이유(LLM의 계산 부정확, 컨텍스트 한계)와 보안 주의점을 추가했다. 오타 "떄문에" → "때문에", "Llm" → "LLM".
2. **"supervisor agent의 system prompt 순서 지정 내용"**
   맞다. 무엇을 적어야 하는지(호출 순서, 조건, 종료 조건)와 순서가 없을 때 생기는 문제, 순서가 고정이면 코드로 고정하는 대안을 보충했다.
3. **"sub agent가 사용하는 Tool들의 역할은 sub agent의 Prompt에"**
   맞다. Supervisor는 sub agent의 역할만, sub agent는 도구 사용법을 안다는 **역할 분리** 이유를 덧붙였다.
4. **"tag같은걸 거는 방식"**
   LangChain `config`의 `tags`/`metadata`와 LangSmith로 필터링하는 구체적인 방법을 추가했다.
5. **"llm judge는 정량평가의 신뢰도가 애매함"**
   맞다. 왜 애매한지(점수 흔들림, 각종 bias)와 대안(binary, pairwise, rubric, 사람 평가와 일치도 확인)을 붙였다.
6. **"답을 만들라고 했을땐 대충만들기 떄문에 그게 더 안좋음"**
   메모만으로는 무엇을 만드는지 분명하지 않아서, **judge에게 정답을 직접 생성시켜 비교하는 방식**을 말한 것으로 해석했다. 다르게 들었다면 알려 주면 고치겠다. 오타 "떄문에" → "때문에".
7. **"trajectory 평가"**
   맞다. 비교 방식(strict / unordered / subset / superset)과 한계(다른 올바른 경로를 틀렸다고 볼 수 있음)를 추가했다.
